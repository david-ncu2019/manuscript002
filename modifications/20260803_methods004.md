# Audit recommendations: methods004.tex vs. tuku_no_update_sensitivity implementation

**Scope:** `sections/methods004.tex` (`subsec:no_update_sensitivity`), `sections/appendix001.tex` (`app:no_update_settings`), `sections/discuss001.tex` (`subsec:discussion_reduced_sampling`), `sections/conclusion001.tex`.
**Compared against:** `007_tests/014_ml_nowcast/experiments/section_pooled/run_048/supplements/tuku_no_update_sensitivity/` (results, provenance manifests verified byte-for-byte against frozen hashes; `scripts/run048_tuku_no_update_sensitivity.py` read in full).
**Verdict:** No factual contradictions found. The design description, sign convention, metric definitions, bootstrap settings, and reported numbers in the manuscript all match the pipeline's actual implementation and output. The items below are precision upgrades and one open provenance question — not corrections of proven errors.

---

## Finding 1 (flag, not a fix): MLCW deformation-model claim has untraced provenance

**Where:** `methods004.tex`, `subsec:deformation_model` — "Differences between consecutive fitted values then represented the MLCW compaction and cGNSS vertical displacement that occurred during each month." Same claim repeated in `dataset003.tex`: "Each displacement series between adjacent magnetic rings was therefore fitted with a deformation time series model comprising linear, periodic, and step functions."

**What the code shows:** `23_build_input_snapshot.py`'s `load_mlcw()` reads an already-cumulative, already-monthly, already-six-section CSV (`01_mlcw_compaction/{station}.csv`) with zero alignment or model-fitting inside that function. The pipeline then computes `mlcw_delta = mlcw.diff()` — a raw first difference, "ZERO outlier-related modification" per the script's own docstring. By contrast, `load_gps()` reads an already-fitted `"modeled"` cGNSS column, consistent with the manuscript's deformation-model claim for cGNSS specifically.

**What this does and does not prove:** This confirms the *ML nowcasting pipeline* applies no additional model fitting to MLCW beyond a raw difference. It does **not** prove the manuscript's claim about MLCW is wrong — the CSV `load_mlcw()` reads is already aligned to monthly dates and six standardized depth sections by the time the pipeline sees it. Whatever process produced that alignment (a deformation-model fit, as claimed, or something else) happens upstream of the ML pipeline and was not traced in this audit or the prior manuscript-editing session.

**Recommendation:** Do not delete or reverse the MLCW deformation-model claim on the strength of this evidence alone — that would replace one unverified claim with another. Before submission, verify directly against the source that produces `01_mlcw_compaction/{station}.csv` (likely `12_stress_strain_per_layer.py` or an equivalent IHM-F/tau_demo_TUKU-era alignment script) whether MLCW ring displacement was in fact fitted with the linear+periodic+step model described in `\Cref{eq:deformation_model}`, or aligned by a different method (e.g., direct interpolation to monthly epochs). If a different method was used, `dataset003.tex` line 8 ("linear, periodic, and step functions") needs correcting for MLCW specifically, while the cGNSS half of that sentence (confirmed correct) stays unchanged.

**Severity:** Medium — affects a factual methods claim, but is a verification gap, not a demonstrated error.

## Finding 2: appendix bootstrap description omits the fixed seed and CI type

**Where:** `appendix001.tex`, `app:no_update_settings`, final paragraph: "Ninety-five percent confidence intervals... were calculated with a paired moving-block bootstrap. The ordered sequence of 22 origins was resampled 2,000 times with a block length of two origins."

**What the code shows:** `paired_moving_block_bootstrap()` in `run048_tuku_no_update_sensitivity.py` uses `n_boot=2000`, `block_length=2` (both match the appendix exactly), a fixed seed (`np.random.default_rng(seed=48)`), and constructs the interval as the 2.5th/97.5th percentile of the bootstrap distribution (a percentile bootstrap, not BCa or normal-approximation).

**Recommendation:** The appendix is already correct on the numbers that matter for reproducibility (2,000 resamples, block length 2, paired/lockstep resampling). Two optional additions would make the method fully reproducible from the text alone:
- After "resampled 2,000 times with a block length of two origins," add: ", using a fixed random seed for reproducibility."
- Specify the interval construction: "Ninety-five percent confidence intervals were calculated with a paired moving-block bootstrap, using the 2.5th and 97.5th percentiles of the resulting bootstrap distribution."

**Severity:** Low — reproducibility completeness, not a correctness issue. Optional.

## Finding 3: per-section results not reported anywhere in the manuscript text

**Where:** `discuss001.tex` reports only pooled (all-sections-combined) MAE/RMSE/bias. `methods004.tex`/`appendix001.tex` state results are computed "for each depth section and for all sections combined," but no per-section numbers appear in any manuscript text read.

**What the code shows:** `metrics_per_section.parquet` contains per-section MAE/RMSE/normalized-MAE and bootstrap CIs for S1–S6. Only 3 of 6 sections (S2, S5, S6) have a horizon-normalized-MAE delta CI that excludes zero; S1, S3, S4 do not.

**Recommendation:** This is not necessarily a gap — the manuscript may intentionally report only the pooled result in the main text, consistent with `subsec:discussion_reduced_sampling`'s framing as a single aggregate finding. Flagging for the author's judgment only: if per-section heterogeneity (e.g., "the twelve-month horizon's error growth is statistically distinguishable from the six-month horizon only in S2, S5, and S6") is scientifically relevant to the paper's argument, it currently appears nowhere and would need one added sentence in `discuss001.tex` or a supplementary table. If the pooled result is sufficient for the paper's claims, no action needed.

**Severity:** Low — informational, author's call.

## Finding 4: precision check on the "~0.35 mm/month at both horizons" claim — confirmed accurate, no action needed

**Where:** `discuss001.tex`: "Per-row monthly estimation error, computed before summing over a horizon, was approximately 0.35~mm/month at both six and twelve months."

**What the code shows:** `summary_metrics.json` gives the exact raw per-row MAE as 0.345528 mm/month (H6) and 0.344126 mm/month (H12) — a difference of 0.0014 mm/month.

**Recommendation:** No change needed. "Approximately 0.35 mm/month at both" is an accurate, appropriately-rounded description of two values that differ by less than 0.002 mm/month. This finding is included in the audit only to document that the claim was checked, not because it needs correction.

**Severity:** None — confirmed correct.

## Finding 5: "MLCW observations... withheld during estimation" is accurate but has one precision nuance worth an optional footnote

**Where:** `methods004.tex`: "MLCW observations within each horizon were withheld during estimation and were used afterward as reference values."

**What the code shows:** MLCW never appears in the feature matrix `X` at any point (confirmed: the P3/level1b predictor registry contains zero MLCW-derived features). However, `fit_bayesian_fold`'s row-completeness check (`dropna` over a `required` column list) includes `y_observed` (the MLCW reference value) — meaning a horizon-month row with a missing MLCW reading would be dropped from the *scored* comparison set, not merely left unused as a feature. In this run, every horizon window passed a completeness check (`assert_no_gap_and_full_horizon`) before fitting, so this never actually triggered — but the precise claim is "MLCW never enters the predictor set," not "MLCW plays no role in the pipeline at all" (it still gates which rows are eligible to be scored).

**Recommendation:** No change strictly needed — "withheld during estimation... used afterward as reference values" is accurate and does not claim MLCW plays zero role. Optional, only if maximum precision is desired: could add a subordinate clause noting MLCW availability was also required for a month to be included in the comparison set. Not necessary for correctness.

**Severity:** None to very low — optional precision only.
